# Hackathon Todo – Phase II Constitution

## Core Principles

### I. Spec-Driven Only

All implementation MUST be preceded by explicit specification. This principle is NON-NEGOTIABLE.

- **Never** write or modify code without an explicit specification
- **Always** read and reference the relevant spec files before implementation
- Specs are the **single source of truth** for all feature behavior
- If behavior is unclear, **update or request a spec change** before coding
- Ambiguous requirements MUST be clarified through the spec, not assumed in code

**Rationale**: Specifications prevent scope creep, ensure traceability, and enable autonomous agents to work with clear boundaries. Without specs, implementations drift from intent.

### II. Agentic Dev Stack Enforcement

The development workflow MUST follow this exact sequence. No step may be skipped.

1. **Write or update specs** - Define what will be built
2. **Generate a structured implementation plan** - Design how it will be built
3. **Break the plan into tasks** - Create atomic, executable work items
4. **Implement tasks exactly as defined** - Execute without deviation

**Rationale**: This sequential workflow ensures that design decisions are captured before implementation begins, reducing rework and enabling parallel task execution by multiple agents or developers.

### III. No Manual Coding

All implementation MUST be generated by Claude Code or equivalent AI agents.

- The human operator **only** provides prompts, reviews output, and updates specs
- Do **not** instruct the user to manually edit files
- All code changes flow through the agent toolchain
- Manual edits bypass traceability and violate the spec-driven model

**Rationale**: Centralizing implementation through agents ensures consistency, maintains audit trails, and keeps the human focused on high-level direction rather than low-level coding.

## Technology Constraints

These technology choices are MANDATORY and MUST NOT be deviated from without constitution amendment.

### Frontend Stack

| Component | Requirement |
|-----------|-------------|
| Framework | Next.js 16+ (App Router) |
| Authentication | Better Auth |
| API Security | JWT tokens attached to every API request |
| HTTP Client | Centralized API client abstraction (no scattered fetch calls) |

### Backend Stack

| Component | Requirement |
|-----------|-------------|
| Framework | Python FastAPI |
| ORM | SQLModel |
| Database | Neon Serverless PostgreSQL |
| Auth Middleware | JWT verification (stateless) |
| Auth Design | Backend MUST NOT call frontend for auth verification |

### Database Requirements

| Constraint | Description |
|------------|-------------|
| Platform | PostgreSQL via Neon |
| Multi-tenancy | Tasks table scoped by `user_id` |
| Ownership | Enforce ownership at query level (WHERE user_id = ?) |

## Authentication & Security Rules

Security rules are NON-NEGOTIABLE. Violations MUST trigger implementation halt.

1. **Better Auth scope**: Runs ONLY on the frontend
2. **Token format**: Better Auth MUST issue JWT tokens
3. **Request header requirement**: Frontend MUST include `Authorization: Bearer <JWT>` on every API request
4. **Backend verification requirements**:
   - Verify JWT signature using shared secret
   - Reject unauthenticated requests with 401 status
   - Extract `user_id` from token claims
   - Enforce task ownership on EVERY operation
5. **Trust boundary**: Backend MUST NEVER trust `user_id` from request body alone

**Shared Secret Configuration**:
- Environment variable: `BETTER_AUTH_SECRET`
- MUST match in both frontend and backend environments

## API Rules

All API design MUST follow these conventions.

**Route Requirements**:
- All routes MUST live under `/api/`
- RESTful conventions only
- JSON responses only
- Errors returned via `HTTPException`
- Every endpoint requires JWT authentication

**Required Endpoints**:

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/api/{user_id}/tasks` | List user's tasks |
| POST | `/api/{user_id}/tasks` | Create new task |
| GET | `/api/{user_id}/tasks/{id}` | Get single task |
| PUT | `/api/{user_id}/tasks/{id}` | Update task |
| DELETE | `/api/{user_id}/tasks/{id}` | Delete task |
| PATCH | `/api/{user_id}/tasks/{id}/complete` | Toggle completion |

**Endpoint Security Contract** (ALL endpoints MUST):
- Validate JWT token
- Match JWT `user_id` with route `user_id` parameter
- Filter data by authenticated user only

**Claude Code Execution Requirements**:

## Quality & Behavior Rules

These guidelines govern code quality standards.

- **Clarity over cleverness**: Prefer readable, maintainable code
- **Production-ready only**: No placeholder or stub implementations
- **Stack discipline**: Do not introduce libraries outside the approved stack
- **No duplication**: Avoid duplicated logic across frontend and backend
- **Secret management**: No hard-coded secrets; environment variables only
- **Database access**: All database operations via SQLModel
- **API client**: All frontend API calls via centralized API client

## Failure Conditions

If ANY of the following occur, **STOP and request clarification**:

1. Missing or conflicting specs
2. Security ambiguity (unclear auth requirements)
3. Auth flow inconsistency (frontend/backend mismatch)
4. Spec contradicts implementation plan

Do NOT proceed with assumptions. Clarification is mandatory.
