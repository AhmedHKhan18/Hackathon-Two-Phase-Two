# Implementation Plan: Local Kubernetes Deployment

**Branch**: `002-local-k8s-deploy` | **Date**: 2026-01-27 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/002-local-k8s-deploy/spec.md`

## Summary

Deploy the Phase III Todo AI Chatbot to a local Minikube Kubernetes cluster using AI-assisted containerization and Helm chart generation. This is an infrastructure-only phase with no application code changes. All Dockerfiles, Helm charts, and Kubernetes manifests will be generated using AI tools (Claude Code as primary, with Docker AI Agent/Gordon and kubectl-ai as alternatives).

## Technical Context

**Language/Version**: Python 3.11+ (backend), Node.js 20+ (frontend)
**Primary Dependencies**: Docker, Minikube, kubectl, Helm 3
**Storage**: External Neon PostgreSQL (unchanged, accessed via DATABASE_URL)
**Testing**: `helm lint`, `kubectl get pods`, manual E2E validation
**Target Platform**: Local Minikube (Kubernetes 1.28+) on Windows
**Project Type**: Web application (frontend + backend monorepo)
**Performance Goals**: Pods reach Running state within 5 minutes
**Constraints**: Local development only, no cloud deployment, no TLS/Ingress
**Scale/Scope**: Single Minikube cluster, 1-3 replicas per service

## Phase 1: Design Artifacts

### 1. Dockerfile Design (Frontend - Next.js)

**Multi-stage build strategy**:
```
Stage 1 (deps): Install dependencies from package.json
Stage 2 (builder): Build Next.js with standalone output
Stage 3 (runner): Alpine-based production image
```

**Key configurations**:
- Base: `node:20-alpine`
- Output mode: `standalone` (via next.config.ts)
- Port: 3000
- Environment variables: Runtime injection via Kubernetes

### 2. Dockerfile Design (Backend - FastAPI)

**Build strategy**:
```
Stage 1: Python slim base, install requirements
Stage 2: Copy application code, run uvicorn
```

**Key configurations**:
- Base: `python:3.11-slim`
- Entry: `uvicorn main:app --host 0.0.0.0 --port 8000`
- Port: 8000
- Environment variables: Runtime injection via Kubernetes

### 3. Helm Chart Design

**Frontend Chart**:
- Deployment: 1 replica (configurable)
- Service: NodePort for external access
- ConfigMap: NEXT_PUBLIC_API_URL pointing to backend service

**Backend Chart**:
- Deployment: 1 replica (configurable)
- Service: ClusterIP (internal) or NodePort (debugging)
- Secret: DATABASE_URL, BETTER_AUTH_SECRET, GEMINI_API_KEY
- ConfigMap: FRONTEND_URL for CORS

### 4. Environment Variable Strategy

| Variable | Type | Source |
|----------|------|--------|
| DATABASE_URL | Secret | User-provided Neon connection string |
| BETTER_AUTH_SECRET | Secret | User-provided JWT secret |
| GEMINI_API_KEY | Secret | User-provided API key |
| NEXT_PUBLIC_API_URL | ConfigMap | Backend K8s Service URL |
| FRONTEND_URL | ConfigMap | Frontend K8s Service URL |

## Implementation Phases (High-Level)

### Phase 1: Environment Setup
- Verify Docker, Minikube, kubectl, Helm installations
- Configure Minikube to use local Docker images

### Phase 2: Containerization
- Generate frontend Dockerfile (AI-assisted)
- Generate backend Dockerfile (AI-assisted)
- Build and test images locally

### Phase 3: Helm Charts
- Generate frontend Helm chart (AI-assisted)
- Generate backend Helm chart (AI-assisted)
- Validate with `helm lint`

### Phase 4: Deployment
- Start Minikube cluster
- Deploy backend chart
- Deploy frontend chart
- Verify pods and services

### Phase 5: Validation
- Access frontend via Minikube service URL
- Verify frontend-backend communication
- Test scaling replicas

## Risk Analysis

| Risk | Mitigation |
|------|------------|
| Docker AI (Gordon) unavailable | Claude Code generates Dockerfiles directly |
| kubectl-ai unavailable | Claude Code generates all kubectl commands |
| Minikube resource constraints | Limit to 1 replica per service initially |
| Database connectivity from Minikube | Verify Neon allows external connections |
| Build time for large dependencies | Use Docker layer caching, multi-stage builds |
